# リソース使用量の改善（2026-09-10）

対象: Issue #48。macOS 26.6.2、同じMacのdebugビルドで確認。

## 実アプリの待機状態

修正前は会議データがない状態でも、起動中のMeetingAgent本体がCPU 99〜100%、RSS約437MiBを使用していた。3秒の `sample` ではメインスレッドのSwiftUI / SystemSegmentedControlのサイズ計算が支配的だった。採取時のphysical footprintは約760MB。RSSとphysical footprintは別指標であり、合算しない。

標準TabViewを通常のボタンと選択画面に置き換え、同値のPublished更新と待機中のメトリクス更新を停止。修正後のCapture画面では、起動後約5分のRSS約101MiB、CPU約0.4%。追加の2秒間隔測定でもCPU 0.4〜0.8%だった。起動直後のウォームアップ、画面選択、WebKit子プロセスや認識エンジンにより数値は変わる。3日稼働した旧プロセスと新プロセスの比較であり、メモリ低下をすべて特定コードの効果やリーク解消とは断定しない。

## 実装

- CaptureとMeetingsの選択は通常のSwiftUIボタンに変更。隠れたMeetings画面のWebViewも保持しない。
- キャプチャ状態は変化時だけPublishedへ反映。待機中に不要なメトリクス更新を行わない。
- OCRは単一のutilityタスクがSQLiteのpending行を1件ずつ取得。メモリ上に画像ごとのタスクを蓄積せず、結果保存時も全画面の再取得を行わない。待ち行列用の索引を追加。
- 保守処理は完了済み履歴を除外。DB変更時や録音中の定期確認、低頻度の復旧確認で実行する。既に待機・実行中の文字起こしジョブの音声は走査しない。保存期間の処理は毎時実行。
- UIの最大100件制限から保守・保存期間処理を分離。古い未処理会議や期限切れの会議を取りこぼさない。
- 文字起こしと画面情報を1回のtimeline取得に統合。WebSocket接続中は定期全件取得を止め、変更通知と再接続時に更新。切断中は5秒間隔でフォールバック。
- キャプチャメトリクスの通知はクエリキャッシュへ直接反映し、会議一覧・タイムラインを再取得しない。
- タイムラインの計算結果は最後の1会議だけキャッシュし、DB変更で失効。遅れて届いたシステム音声・マイク・OCRを再反映する。
- 重複判定は時刻の二分探索で候補範囲を限定。全履歴との総当たりを避ける。
- 発話・画面のDOM表示はそれぞれ50件単位。根拠への移動時は対象ページへ移動。
- 画像は表示領域付近だけ取得し、領域外でDOM・Blobキャッシュ・object URLを解放。読み込み中の不要な通信はAbortSignalでキャンセル。

## 検証

`swift run --package-path apps/macos MeetingVerification resources`:

- 120会議の履歴から完了分を除外し、100件制限外の未処理会議を取得。
- 200画面のOCR待ち行列を順番に取得・完了。
- 遅れて保存されたマイク発話とOCRでタイムラインキャッシュが失効。
- 2時間分の時刻を持つ1,440発話で720組の重複注釈を保持。手元のdebug実行で約8ms。

通常のMeetingVerificationには上記に加え、30分分の2トラックPCM再生、欠落・再起動回復・保存済み音声の再処理、要約・Codexの既存検証を含む。

Webテストは画像の遅延取得と解放、50件単位の表示、共有timeline取得、メトリクス通知時の再取得抑止、再接続時の更新を確認する。

2時間の合成データ検証は実時間2時間の録音・音声認識テストではない。実会議中のピーク使用量、モデル別の負荷、長時間のメモリリークの不在はまだ保証しない。
